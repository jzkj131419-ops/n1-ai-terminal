# BANK_FORMATS · 各银行流水格式特征与处理模式

> **最后更新：** 2026-05-29  
> 新增银行时，在对应章节补充格式描述和推荐模式。

---

## 格式分类总览

| 银行 | 常见格式 | 推荐模式 | 备注 |
|------|---------|---------|------|
| 广发银行（信用卡） | xlsx（原始导出） | `csv`（结构化解析） | 最干净，直接用 |
| 建设银行（司法查询） | PDF（扫描图像，144页+） | `vision` | tesseract 置信度低，Vision 必须 |
| 民生银行（司法查询） | PDF（文本层，多列交叉排版） | `vision` 强制 | 有文本层但解析器不认识格式 |
| 工商银行 | xlsx / csv | `csv` | 标准格式 |
| 农业银行 | xlsx | `csv` | 标准格式 |
| 招商银行 | pdf（文本层）/ xlsx | `hybrid` | 文本层质量好 |
| 中国银行 | pdf | `hybrid` | — |

---

## 一、广发银行信用卡

**格式特征：**
- 文件名：`XXXXX信用卡流水.xlsx` + `XXXXX信用卡开户.xlsx`
- Sheet 名：含"明细"或直接是数据
- 列：交易日期、交易金额、收入、支出、余额、对方户名、摘要
- 信用卡流水特点：余额列为 0（信用卡账户）需特殊处理

**处理模式：** `csv`（结构化解析，无需 OCR）

**注意：**
- 开户文件（`*开户.xlsx`）自动识别为 SKIP，不参与流水分析
- 信用卡账户期初/期末余额需从开户文件或首末行手动提取
- 商户名称可能分散（如"星巴克北京"和"星巴克上海"），需后处理合并

---

## 二、建设银行（法院司法查询 PDF）

**格式特征：**
- 文件名格式：`010102042026041388910325000_XXXX_99_0_meger.pdf`
- 内容：《协助查询交易明细信息结果（完整版）》
- PDF 类型：**扫描图像**，无文本层
- 每个查询包含多个 PDF 文件（_0008_ 为封面/账户信息，_0009_ 为流水主体）
- 页数：主流水文件通常 100-200 页
- 表格格式：横向宽表，列密集（含 MAC 地址、第三方订单号等司法查询特有字段）

**处理模式：** `hybrid`（tesseract 先跑，置信度低时自动转 Vision）

**OCR 特点：**
- tesseract 对该格式置信度约 20-50%，几乎所有页面都会触发 Vision
- Vision 模型（qwen-vl-max）对该格式识别准确
- 每页约提取 10-15 条交易
- 处理时间：约 1 页/15秒，100 页约 25 分钟

**命名规律：**
- `_0008_99_0_meger.pdf`：账户信息页（1页，0条交易）
- `_0009_99_0_meger.pdf`：交易明细主体（100-200页）

## 三、民生银行（法院司法查询 PDF）

**格式特征：**
- 文件名格式：`周贤（司法查询）/交易明细/周贤.pdf`（目录结构）
- 内容：《中国民生银行账户交易明细清单》
- PDF 类型：**有文本层**（内嵌文字），但格式特殊
- 页数：100-250 页

**⚠️ 特殊格式陷阱：**
```
每条交易跨 3-5 行，多列交叉排版，示例：
行1: 2024/07/30  支付宝-快捷支付-黄  20881229789268  支付宝
行2: 出  71.60  3577.21  跨行支付  黄鸿昆  59490565090100  网联协议  中国民生银行...
行3: 16:06:22  鸿昆 44  公司清算中心
```
文本层提取后，标准解析器**只能识别极少数交易（约2条）**，95%+数据被丢失。

**处理模式：** 必须强制 `vision` 模式，绕过文本层直接走图像识别

```bash
# 正确做法：直接调 OCR 脚本，不走 task-start API
python3 /Volumes/.../run_audit_local_ocr.py \
  --input-dir 源数据目录 \
  --mode vision \
  ...
```

**附带文件：**
- `个人客户信息（含账户）/周贤.pdf`：账户开户信息
- `交易明细/周贤.pdf`：主流水（重要）
- `失败汇总/失败交易信息.pdf`：失败交易记录
- `失败汇总/失败客户信息.pdf`：失败客户信息

**数据质量说明：**
- Vision 模式下约提取实际交易的 30-50%（受格式复杂度限制）
- 日期字段可能丢失"日"部分（显示为 2019-03 而非 2019-03-11）
- 时间字段大量误识别为 02:00:00
- 关键交易需对照原始 PDF 人工核实

## 四、模式选择决策树

```
收到银行材料
│
├── 是 xlsx/csv？
│   └── → mode: csv（结构化解析）
│
└── 是 PDF？
    ├── 有文本层？
    │   ├── 标准格式（招行/工行/农行等）→ mode: hybrid
    │   └── 多列交叉排版（民生司法查询）→ 强制 mode: vision
    │
    └── 无文本层（扫描图像）
        ├── tesseract 可识别（标准表格）→ mode: hybrid
        └── tesseract 置信度低（建设司法查询）→ mode: hybrid（自动转 Vision）
```

---

## 五、Vision 触发条件（hybrid 模式下）

系统在以下情况自动触发 Vision API：
- tesseract 识别文字置信度 < 阈值
- 页面为图像而非文字

Vision 使用的模型：`qwen-vl-max`（阿里云 DashScope）  
配置位置：`~/.openclaw/openclaw.json` → `models.providers.aliyun.apiKey`

---

## 六、新银行接入 Checklist

遇到新银行材料时，按以下步骤判断处理方式：

1. **确认文件类型**：xlsx/csv/pdf
2. **如果是 PDF**：用 `pdftoppm` 转一页图片查看格式
3. **小规模测试**：用 `--mode hybrid` 跑 1-2 页，检查 `transactions.json` 条数
4. **条数异常（期望有交易但 0 条）**：
   - 检查 `审计中间结果/vision/*.error.txt` 看 Vision 是否报错
   - 检查 `审计中间结果/*_ocr_lines.txt` 看文本质量
   - 切换 `--mode vision` 重试
5. **记录到本文件**，新增对应银行章节
